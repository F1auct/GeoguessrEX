## 第一部分：项目概述 + 游戏体验（P2–P5）

**讲解人 A**

---

各位好，我们来汇报 GeoGuessr MVP 这个项目。

（P2）先说项目定位。这是一个**基于 Google 街景的地理判断 Web 游戏**——玩家看到一张街景画面，判断自己在哪里，然后在地图上标记位置。核心玩法就四步：**看街景 → 找线索 → 标位置 → 看结果**。当前是 MVP v2.0，单人模式，内置 5 道示例题目。技术标签：React 前端、Express 后端、高德地图、Google 街景、Haversine 距离算法。

（P3）游戏流程分五步。第一步，选择题库组；第二步，进入全屏 Google 街景画面；第三步，观察建筑、植被、路牌、语言等各种线索；第四步，在高德地图上点击放置标记；第五步，查看结果——距离、得分、猜测点和正确答案的连线对比。整个流程引导玩家完成一次从观察到推理到验证的地理探索闭环。

（P4）看一下实际游戏界面。这是猜点阶段：左上角 HUD 显示玩家信息、题库组、题目进度和当前状态。全屏是 Google 街景的沉浸式画面。右下角是一个可折叠的小地图和浮动提交面板——玩家在这里点击地图放标记，然后提交答案。

（P5）提交后进入复盘阶段。左边是结果地图，绿色标记是你的猜测位置，红色标记是正确答案，中间虚线连线直观展示偏差。右边卡片显示距离、得分、坐标和地点介绍，底部可以点"下一题"继续。

好，项目概况和游戏体验就介绍到这里。接下来由第二位同学讲解评分机制和技术架构。

## 第二部分：评分机制 + 技术架构（P6–P7）

**讲解人 B**

---

接上一部分，大家已经看到了游戏怎么玩，下面我来讲**分数怎么算、系统怎么搭**。

（P6）评分机制核心是两个公式。第一个是 **Haversine 大圆距离公式**——球面三角学经典算法，输入两个 WGS-84 坐标，输出球面最短距离（单位千米）。地球半径取 6371 公里。

第二个是**指数衰减得分公式**：`Score = max(0, round(5000 × e^(-d/2000)))`。满分 5000 分，距离越近得分越高。当距离 d=0 时得满分 5000；d=2000 公里时约 1840 分；d 趋向无穷大，分数趋近于 0。指数衰减的好处是远端仍然有区分度，不会出现稍微猜远一点就零分的情况。

（P7）系统架构分三层。**数据层**：questions.json 和 users.json，轻量级 JSON 文件持久化，无数据库依赖。**后端**：Express 框架，PBKDF2 密码加密认证，完整的 CRUD API，Haversine 评分逻辑。**前端**：Vite + React 18，高德地图 JSAPI 做猜点和结果展示，Google Maps Embed API 加载街景，Leaflet 作为备用地图方案。整体是前端 → 后端 → 存储的经典三层架构，Bearer Token 贯穿认证链路。

技术架构讲完了，下面由第三位同学深入讲核心代码逻辑。

## 第三部分：核心代码逻辑（P8–P11）

**讲解人 C**

---

前面讲了评分公式和架构，我来落到代码层面，展示四个核心逻辑模块。

（P8）第一个，**数学公式的代码实现**。左边是 Haversine 函数——`haversineDistanceKm(lat1, lng1, lat2, lng2)`，就是把刚才的数学公式翻译成 JavaScript。先用 `toRad` 把角度转弧度，然后套入 Haversine 标准公式，最后乘以地球半径。右边是评分函数 `scoreFromDistance`——一行核心代码：`maxScore * Math.exp(-distanceKm / decay)`，满分 5000，衰减常数 2000。整个文件不到 6 行逻辑，简洁但准确。

（P9）第二个，**坐标转换**。这是这个项目最有中国特色的工程问题。高德地图（AMap JSAPI）依法必须使用 GCJ-02 坐标系，而 Google 街景和后端距离计算使用的是 WGS-84。两者在国内会偏移 100 到 700 米。我们的方案是左边这个 `wgs84ToGcj02` 函数，基于国家测绘局的非线性偏移算法，同时通过 `outOfChina` 做境外检测——在中国境外直接透传不做转换。右边是逆向函数 `gcj02ToWgs84`，利用正向函数反推：`2*lng - converted.lng` 即可还原。

底部这条链路展示了完整的转换流程：**题库存储 WGS-84 → 转 GCJ-02 展示到高德地图 → 用户点击标记（GCJ-02）→ 转回 WGS-84 → 后端 Haversine 计算**。五个环节，两次转换，确保前后端坐标体系一致。

（P10）第三个，**判分流水线**。一次 `POST /api/submit` 请求，后端 `gradeAnswer` 函数串联五步：① `getQuestionById` 从 JSON 题库查题；② 校验 guess 参数的经纬度类型，NaN 直接返回 400；③ `haversineDistanceKm` 计算球面距离；④ `scoreFromDistance` 指数衰减评分；⑤ 组装完整结果包返回前端——包含 questionId、score、distanceKm、正确答案坐标和街景参数。一次 HTTP 请求，五步串联，前端拿到完整结果，无需额外请求。

（P11）第四个，**游戏状态机**。这是前端最复杂的组件 GamePage 的状态流转。五个状态：loading（加载题库）、ready（街景和地图就绪，等待用户操作）、submitting（提交答案中，按钮禁用）、result（展示结果地图和得分面板）。主流程是 loading → ready → submitting → result，然后通过"下一题"回到 ready 继续循环。异常分支：loading 失败进入 error 状态，submitting 失败回到 ready 显示错误提示。每个状态对应一套独立的 UI 布局，状态变量驱动整个页面的条件渲染。

核心代码逻辑就讲到这里。最后请第四位同学总结功能全景和后续规划。

## 第四部分：功能矩阵 + 数据 + 规划（P12–P14）

**讲解人 D**

---

我来收尾，总结一下项目目前有什么、做到了什么程度、接下来做什么。

（P12）功能矩阵可以用六个维度概括。**题库管理**：题库组的完整 CRUD，支持 Google Maps URL 智能解析，粘贴链接即可自动提取经纬度和视角参数，还有街景实时预览。**街景展示**：Google Maps Embed API 实现全屏沉浸模式，heading/pitch/fov/panoId 四个视角参数可配置。**地图猜点**：高德 JSAPI 点击放置标记，内置 WGS-84 和 GCJ-02 实时坐标转换。**智能评分**：Haversine 距离计算 + 指数衰减分数，满分 5000。**用户系统**：注册登录、PBKDF2 密码加密、Bearer Token 七天有效期。**响应式适配**：桌面 1280px、平板 980px、手机 640px 三档自适应。

（P13）几个关键数据。目前 5 道示例题目，单题满分 5000，响应式三档断点，Token 有效期 7 天。五题实测结论：算法计算准确、坐标转换稳定、街景加载流畅、评分曲线合理、三端显示正常。同时也坦诚列出已知问题：国内 Google 街景偶发加载超时；移动端虚拟键盘弹出会遮挡地图；题库管理缺少批量导入功能；用户列表还没有分页。

（P14）未来规划分三个阶段。**Phase 1**，完善核心体验——扩充题库、优化移动端交互、增加音效和动画。**Phase 2**，多人对战——实时房间、排行榜、WebSocket 推送。**Phase 3**，商业化探索——会员订阅、广告位、自定义题库付费功能。MVP 已经验证通过，具备向完整产品演进的技术基础和用户体验框架。
