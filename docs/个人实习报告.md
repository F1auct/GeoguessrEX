## 目标

本次项目实训以 **GeoguessrEX** 地理图寻游戏平台为课题。该平台是一款基于 Web 的在线地理探索游戏，用户通过 Google 街景或上传图片观察环境细节，结合地图知识判断所在位置，在高德地图上放置标记进行猜测，系统根据猜测坐标与真实坐标之间的距离计算得分。在团队完成基础框架搭建（用户认证系统、题库 CRUD、单人图寻核心玩法）之后，本人加入开发组，主要负责平台的功能扩展与完善工作。

通过参与该项目的实训，本人设定了以下学习目标：

1. **全栈开发能力提升**：在真实的项目场景中实践 React + Express + SQLite 技术栈，理解从前端用户交互到后端数据处理再到数据库持久化的完整数据链路。对每一个功能模块，亲自完成数据库表设计、服务层业务逻辑编写、RESTful API 路由暴露、前端页面组件开发四个层次的开发工作，形成对 Web 全栈开发的系统认知。

2. **软件需求分析能力**：学习如何将用户的非形式化需求转化为结构化的产品需求文档（PRD）。具体包括：梳理用户角色与使用场景、划分功能模块边界、定义数据模型与接口契约、制定非功能需求指标。通过撰写两版 PRD 的迭代过程，体会需求文档为何需要随着项目演进而持续更新。

3. **技术沟通与汇报能力**：在各里程碑节点配合团队制作 PPT 汇报材料，将技术实现转化为评审老师易于理解的图表与演示。学习如何用架构图、流程图、ER 图等可视化手段准确传达系统设计思路。通过 PlantUML 文本绘图工具实践"文档即代码"的理念，使技术图表能够纳入 Git 版本管理。

## 内容

在项目实训期间，本人围绕 GeoguessrEX 平台参与了功能模块开发、需求文档撰写、PPT 汇报材料制作和技术架构图设计四类工作。

### 一、功能模块开发

在团队已完成的用户认证与题库管理基础之上，本人主要负责 **竞技模式** 与 **特色玩法** 两个业务方向的开发工作。每个模块遵循统一的四层开发模式：数据库迁移（Migration）→ 业务服务（Service）→ API 路由（Route）→ 前端页面（Page），共计完成 8 次功能提交，涉及 3 个新前端页面、2 个后端服务文件、2 个后端路由文件的创建，以及 6 张新数据库表的设计。

#### 环球之旅（World Tour）

环球之旅是一种预设路线的探索玩法，用户无需自选题库，而是沿着精心设计的主题路线逐站游玩。每条路线包含若干个地理位置站点，用户在每个站点观察街景并猜测位置，系统评分后展示该地点的历史文化知识。

**数据库设计**：新增 `routes`（路线主表）、`route_stops`（路线站点表）、`user_route_progress`（用户游玩进度表）三张表。routes 表记录路线标题、副标题、描述、封面图、难度等级、XP 奖励、金币奖励、状态等字段。route_stops 表按 order_index 排序存储每站的坐标、视角参数、文化笔记内容。user_route_progress 表通过 UNIQUE(user_id, route_id) 约束保证每用户每条路线仅有一条进度记录，使用 JSON 字符串存储已完成的站点详情列表。

**预置数据**：系统预置三条主题路线各 6 站——丝绸之路（西安钟楼→敦煌莫高窟→喀什老城→撒马尔罕→德黑兰→伊斯坦布尔）、环太平洋之旅（东京涩谷→马尼拉王城→雅加达老城→奥克兰→圣地亚哥→西雅图）、欧洲古堡之旅（爱丁堡城堡→香波堡→新天鹅堡→布拉格城堡→渔人堡→锡吉什瓦拉）。每条路线附带完整的文化笔记，如"敦煌是丝绸之路的咽喉要道，莫高窟现存洞窟 735 个，壁画 4.5 万平方米"。

**后端服务**：routeService 提供 `listRoutes()`（列出活跃路线）、`getRouteById()`（路线详情含站点）、`startRoute()`（开始或恢复路线）、`getProgress()`（获取进度）、`submitStopAnswer()`（提交当前站猜测）五个核心方法。提交答案时复用 Haversine 距离评分算法，计算完成后更新进度记录，若为最后一站则自动标记 completed_at 时间戳并发放 XP 奖励。

**前端页面**：WorldTourPage 实现了三视图切换（list → detail → playing），游玩视图复用已有的 GoogleStreetView 街景组件和 AmapGuessMap 猜点地图组件。每站提交后，结果覆盖层展示猜测点与答案点的双标记地图、距离公里数、单站得分、累计总分，以及该地点的文化笔记卡片。全部站点完成后展示护照印章收集动画，增强了游戏的探索仪式感。

#### 排位赛（Ranked）

排位赛为玩家提供了一种段位制的竞技匹配玩法，通过胜负升降星来激励玩家持续提升地理判断能力。

**段位体系**：设计七段位金字塔结构——青铜 → 白银 → 黄金 → 铂金 → 钻石 → 大师 → 王者。每段位满 5 颗星，胜场加 1 星，满星后自动晋级至下一段位；败场减 1 星，0 星时若再败则降段。在 users 表新增 rank_tier、rank_stars、rank_updated_at 三个字段追踪玩家当前段位状态。

**匹配机制**：rank_queue 表作为匹配队列，玩家点击"开始匹配"后加入队列，系统每隔一定时间扫描队列，将段位相近（差距不超过 2 个段位）的两名玩家配对。配对成功后创建对局房间，双方进入同一场图寻对战。rank_matches 表完整记录每局胜负双方的对战前段位状态和段位变化量，便于后续数据分析和排行榜生成。

**前端页面**：RankedPage 展示玩家当前段位徽章（7 种不同配色）、星数进度条、匹配等待动画、本周胜率统计、历史对战记录列表。匹配按钮点击后进入等待状态，显示"正在为您匹配同段位对手…"的加载动画；配对成功后自动跳转至对战页面。

#### 巅峰赛（Peak）

巅峰赛是面向高水平玩家的精英竞技模式，采用国际象棋等竞技项目中广泛使用的 ELO 积分系统。

**准入机制**：玩家需同时满足三个条件方可参与——当前段位达到钻石及以上、累计完成至少 20 局排位赛、当前时间在每日 18:00 至 24:00 的开放窗口内。peakService 的 `checkEligibility()` 方法一次性校验三项条件，不满足时返回具体的拒绝原因供前端展示。

**ELO 积分系统**：每位玩家初始积分 1200 分，K 因子设为 32。对战前根据双方积分差计算期望胜率（E_A = 1 / (1 + 10^((R_B − R_A) / 400))），对战后根据实际胜负结果调整积分（R_A' = R_A + K × (S_A − E_A)）。peak_matches 表记录每局双方的赛前积分、赛后积分和积分变动量。

**盲选模式**：巅峰赛对战中隐藏对手的昵称和头像信息，仅在对战结束后才揭晓对手身份，增加了比赛的公平性和悬念感。

**前端页面**：PeakPage 提供资格校验入口、当前 ELO 积分展示、积分排行榜、个人历史对战记录、匹配等待动画等功能。非开放时间或资格不足时，页面以清晰的提示文案告知玩家原因和可参与时间。

#### 赛季任务系统（Season Quests）

赛季任务系统为玩家提供每日、每周、每赛季三个时间维度的目标引导，完成任务可获得经验值和金币奖励。

**任务设计**：系统预置 13 个任务，分为三类——日常任务 5 个（排位高手：完成 3 局排位赛；亚洲通：在亚洲国家猜对 5 次；精准一击：单局得分 ≥ 4000；对战之星：赢得 1 局 PvP；贡献者：提交 1 道题目），周常任务 5 个（排位狂热：排位赛胜利 10 局；环球旅行家：在 5 个不同国家猜对位置；坚持不懈：连续 7 天签到；巅峰之路：完成 3 局巅峰赛；环球旅者：完成 1 条环球之旅路线），赛季任务 3 个（黄金强者：达到黄金段位；排位百战：完成 100 局排位赛；巅峰强者：巅峰赛胜利 3 局）。

**进度追踪**：season_quests 表存储任务定义（任务类型、目标类型、目标次数、经验值奖励、金币奖励），user_quest_progress 表存储每个用户对每个任务在某日期的进度（当前完成次数、是否已完成、是否已领取奖励）。各类游戏行为（排位对战、PvP 胜利、巅峰赛、签到、提交题目、环球之旅完成等）完成后自动调用 questService 的进度追踪方法，根据行为的 target_type 匹配对应任务并增加进度计数。

**前端展示**：在 SeasonPage 中增加任务面板 Tab，每个任务显示标题、描述、进度条（current_count / target_count）、经验值和金币奖励数额。任务完成后进度条变绿并出现"领取"按钮，领取后任务卡片变为半透明已领取状态。

#### 国家连击（Country Streak）

国家连击是一种休闲型的无限挑战模式，玩家面对随机街景场景，需要判断该地点位于哪个国家，连续猜对即可累积连击数，一旦猜错连击中断归零。

**判定逻辑**：系统预定义了 10 个国家的地理边界框（Bounding Box），玩家的猜测坐标落入哪个国家的边界框即判定为该国家。若猜测国家与正确答案所属国家一致则连击 +1，更新最佳连击记录；不一致则连击归零。

**前端页面**：CountryStreakPage 展示街景画面、当前连击数、历史最佳连击数，底部提供国家选择按钮。页面顶部持续显示实时连击数字，中断时播放重置动画。复用 GoogleStreetView 和 AmapGuessMap 两个通用地图组件。

#### Design Tokens 重构

对前端样式文件进行了工程化整理，将分散在多个 CSS 文件中的颜色、间距、圆角、阴影等设计变量统一提取到 `tokens.css` 文件中，以 CSS 自定义属性（CSS Custom Properties）的形式定义全局设计令牌（如 `--accent`、`--green`、`--muted`、`--radius-md`、`--shadow-card` 等）。同时清理了原有的重复按钮样式定义，改为统一引用 tokens 变量。此次重构提升了样式的可维护性，后续调整主题色或间距规范只需修改 tokens 文件即可全局生效。

## 方法

### 开发模式与流程

项目采用前后端分离的 B/S 架构，以 monorepo（pnpm workspace）方式组织代码，`apps/web` 为前端 Vite + React 应用，`apps/api` 为后端 Express API 服务。两个应用通过 HTTP RESTful 接口通信，数据格式统一为 JSON。

本人的开发工作遵循标准的功能模块开发流程：

1. **需求分析**：理解功能需求，明确该模块涉及的用户角色、交互流程、数据模型和 API 契约。
2. **数据库建模**：编写 migration 函数，使用 `CREATE TABLE IF NOT EXISTS` 确保幂等性，通过 `ALTER TABLE` 和 `PRAGMA table_info` 检测已存在列实现向前兼容。所有 migration 函数集中在 `database.js` 中按顺序调用，确保数据库版本演进的可追溯性。
3. **服务层实现**：在 `apps/api/src/services/` 下创建或扩展服务文件。服务层直接通过 `better-sqlite3` 的同步 API 访问数据库（`db.prepare().all/get/run()`），封装业务逻辑后返回纯数据对象。对于涉及多个表操作的事务（如悬赏结算需同时更新 bounty 状态、winner 字段和钱包余额），使用 `db.exec("BEGIN")` / `db.exec("COMMIT")` / `db.exec("ROLLBACK")` 保证原子性。

### 关键缺陷分析与修复

在开发和测试过程中，遇到并解决了以下三个有代表性的技术问题：

**问题一：环球之旅提交答案后页面空白**

- **现象**：用户在环球之旅的游玩视图中提交猜测后，页面变为空白，无任何结果显示。
- **排查过程**：通过 React DevTools 检查 WorldTourPage 组件的 state，发现 `handleSubmit` 函数在 API 调用返回后将 `view` 状态从 `"playing"` 切换为 `"result"`。但由于结果覆盖层的 JSX 代码写在 `if (view === "playing" && currentStop)` 条件块内部，当 view 改变后，整个 playing 视图的条件判断失败，不再渲染——包括结果覆盖层在内。最终组件走到了末尾的 `return null`。
- **修复方案**：删除 `handleSubmit` 中的 `setView("result")` 调用，保持 view 为 `"playing"`。结果覆盖层的显示条件从 `view === "result" && lastResult` 改为直接判断 `lastResult` 是否为真。修复后提交答案时结果弹窗在游戏画面之上正确弹出，点击"下一站"关闭弹窗继续游玩。

**问题二：结果弹窗短暂显示后消失**

- **现象**：修复问题一后弹窗可以显示了，但闪现约半秒后自动消失。
- **排查过程**：在浏览器 DevTools 的 Console 面板中捕获到 `AmapResultMap` 组件内部的 TypeError——`result.answer` 为 `undefined`。检查代码发现，`AmapResultMap` 组件期望接收的 result 对象包含 `answer.lat` 和 `answer.lng` 字段（这是单人图寻模式的标准响应格式），而环球之旅的 `routeService.submitStopAnswer()` 返回的响应中正确答案字段名为 `stop` 而非 `answer`。组件尝试访问 `undefined.lat` 导致 JS 运行时错误，React 渲染崩溃，弹窗对应的 DOM 被移除。
- **修复方案**：在 `routeService.submitStopAnswer()` 的返回对象中增加 `answer: { lat: stop.lat, lng: stop.lng }` 字段，使其与 `AmapResultMap` 组件的字段约定保持一致，同时保留原有的 `stop` 字段供环球之旅专用逻辑使用。

**问题三：SeasonPage 编译报错无法启动**

- **现象**：Vite 开发服务器启动时 esbuild 依赖扫描报错——`Expected ")" but found "{"`，指向 `SeasonPage.jsx` 第 172 行。
- **排查过程**：逐行检查该文件的 JSX 结构后发现两个语法问题：（1）第 153 行的 `{tab === "pass" ? (` 三元表达式在 `</section>` 后缺少闭合的 `) : null}`；（2）第 191 行存在一对多余的孤立 `</section>` 和 `) : null}`，不属于任何 JSX 标签的闭合，是之前编辑时遗留的冗余代码。
- **修复方案**：在 pass Tab 的 `</section>` 之后补上缺失的 `) : null}`，并删除孤立的多余标签对。修复后 Vite 正常编译，SeasonPage 的三个 Tab 面板均可正常切换渲染。

### 技能与认知收获

1. **React 组件状态管理**：通过环球之旅模块的多视图切换实践了复杂前端状态机的设计与管理。深刻认识到在 JSX 条件渲染中，状态变量必须与渲染条件的嵌套层级保持一致——当使用 `if (view === "playing")` 包裹一整块 UI 时，该块内部的子条件不应该再去改变 `view` 的值，否则会导致自我排除的逻辑悖论。

## 核心算法/主要功能

本节对本人参与开发的功能模块中涉及的核心算法和技术方案进行详细说明。

### Haversine 距离计算

系统采用 Haversine 大圆距离公式计算用户在地图上放置的猜测坐标与题目真实坐标之间的球面距离。该公式考虑了地球曲率，相比于平面欧几里得距离在大尺度地理计算中更为准确。

公式推导过程：已知地球半径 R = 6371 km，两点坐标分别为 (lat1, lng1) 和 (lat2, lng2)，先将经纬度从角度制转换为弧度制，然后计算：

```
Δlat = lat2 − lat1    （弧度）
Δlng = lng2 − lng1    （弧度）
a = sin²(Δlat / 2) + cos(lat1) × cos(lat2) × sin²(Δlng / 2)
c = 2 × atan2(√a, √(1 − a))
distance = R × c
```

该算法在本项目中的应用范围覆盖了所有需要计算地理距离的场景：单人练习评分、排位赛对战评分、巅峰赛对战评分、PvP 对战评分、大逃杀评分、国家连击国家判定、环球之旅站点评分、悬赏答题评分、每日挑战评分。通过在 `gameService.js` 中封装 `gradeAnswer()` 统一入口，所有玩法模块复用同一套距离计算和评分逻辑，保证了评分标准的一致性。

### 指数衰减评分函数

单纯的距离数值（如"误差 150 公里"）对普通玩家来说不够直观，因此系统通过指数衰减函数将距离转换为 0 到 5000 之间的游戏得分：

```
score = 5000 × e^(−distance / 2000)
```

该函数具有以下数学特性：当 distance = 0 km（完美猜测）时，score = 5000（满分）；当 distance = 2000 km 时，score ≈ 5000 × e^(−1) ≈ 1840 分；当 distance 趋近于无穷大时，score 趋近于 0（但始终为正值）；函数的导数在距离较小时衰减最快，使得"接近但未命中"和"差得很远"之间有显著分差，激励玩家追求精确。

衰减常数 2000 km 的选择考虑到了本项目的全球地理尺度——地球赤道周长约 40000 km，最远两点（对跖点）距离约 20000 km，2000 km 的衰减常数意味着满分的一半大约在 1386 km 处取得，对于一款面向全球的地理猜谜游戏来说，这个区分度是合理的。

### 排位赛段位升降星算法

排位赛的竞技模型设计参考了主流竞技游戏（如英雄联盟、王者荣耀等）的段位系统并做了简化适配。

段位结构为一个有序列表：`['bronze', 'silver', 'gold', 'platinum', 'diamond', 'master', 'grandmaster']`，每个段位对应 0–6 的数值索引。每段位固定 5 颗星容量（代码中以 `STARS_PER_TIER = 5` 常量定义）。

升星逻辑（胜场）：若当前星数 < 4，星数 +1；若当前星数 = 4（满星），星数归 0 且段位索引 +1（晋级）；若当前已是最高段位（grandmaster）且满星，段位不变，星数保持 5。

降星逻辑（败场）：若当前星数 > 0，星数 -1；若当前星数 = 0，段位索引 -1（降段）且星数设为 4（降段后剩余 4 星）。最低段位（bronze）0 星时败场不降段，星数保持 0。

匹配队列的配对策略基于段位索引差：两个玩家的段位索引之差的绝对值 ≤ 2 即可配对（例如黄金玩家可与白银、黄金、铂金、甚至钻石玩家配对，但不能与王者配对）。

### 巅峰赛 ELO 积分算法

巅峰赛采用 Arpad Elo 于 1960 年为国际象棋设计的 ELO 评分系统，该系统目前被广泛应用于各类竞技排名（国际棋联、Lichess、Overwatch 等）。

核心公式分为两步。第一步：计算 A 对 B 的期望胜率：

```
E_A = 1 / (1 + 10^((R_B − R_A) / 400))
```

其中 R_A 和 R_B 分别为 A 和 B 的当前积分。当两人积分相同时，E_A = 0.5（势均力敌）；当 R_A 比 R_B 高 400 分时，E_A ≈ 0.91（A 有 91% 的胜率预期）；反之，若 R_A 比 R_B 低 400 分，E_A ≈ 0.09。

第二步：根据实际比赛结果更新积分：

```
R_A' = R_A + K × (S_A − E_A)
```

其中 S_A 为实际得分（胜 = 1，败 = 0），K 为发展系数（本项目取 K = 32）。积分的涨跌取决于实际表现与预期表现的差值——高分玩家赢了低分玩家，由于期望胜率本就很高，涨分很少；低分玩家爆冷赢了高分玩家，由于期望胜率很低，涨分很多。这种机制天然地驱动积分向玩家的真实实力水平收敛。

本项目的实现中，积分初始值设为 1200 分，K = 32（较低的 K 值使积分变化更稳定，减少偶然性的影响），peak_matches 表完整记录每局的赛前/赛后积分和变化量，便于后续分析 K 值的合理性和调整策略。

### 赛季任务进度追踪机制

赛季任务系统实现了一套基于事件驱动的进度追踪机制。核心设计思路是：各游戏行为在完成时调用 `questService` 的统一追踪接口，传入行为类型（target_type），服务端遍历所有该类型的活跃任务，逐一更新进度。

数据模型上，`season_quests` 表通过 `quest_type` 字段（daily/weekly/season）区分任务周期，通过 `target_type` 字段（如 ranked_games、pvp_win、asia_correct、checkin_streak、peak_games、route_complete 等）建立任务目标与游戏行为的映射关系。`user_quest_progress` 表通过 UNIQUE(user_id, quest_id, date) 约束确保同一用户在同一天（或同周、同赛季）对同一任务仅有一条进度记录，避免重复计数。

任务完成判定：`current_count >= target_count` 时，`completed` 字段置为 1。前端展示"领取"按钮。用户点击领取后，`claimed` 置为 1，经验值和金币奖励通过 `xpService.addXP()` 和 `walletService` 发放。已领取的任务卡片变为半透明状态，从视觉上告知用户该任务已完成。

### WGS-84 与 GCJ-02 坐标转换

中国大陆的电子地图服务（包括高德地图）根据国家测绘法规定必须使用 GCJ-02 坐标系（又称火星坐标系），而 GPS 设备和 Google 街景使用的原始坐标是 WGS-84 坐标系。两种坐标系之间存在最高约 500 米的偏移，在某些敏感区域偏移更大。

本项目的处理策略是：后端统一存储和使用 WGS-84 坐标（原始 GPS 数据，计算 Haversine 距离时不需要转换），前端在使用高德地图展示时通过 `coordTransform.js` 中的 `wgs84ToGcj02()` 函数将 WGS-84 坐标转为 GCJ-02 后再传入高德 API；用户在高德地图上的选点坐标为 GCJ-02，提交至后端前通过 `gcj02ToWgs84()` 反向转换回 WGS-84。这一双向转换方案保证了地图展示的合规性与评分计算的精度。
