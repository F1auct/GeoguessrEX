## 第1部分 · 汇报人 A（开场 + 项目背景 + 认证模块）

**对应 PPT**：概要设计上 Slide 1-4 ｜ **时长**：约 6-7 分钟

### Slide 1 — 封面（1 分钟）

各位老师好，我们是 GeoguessrEX 项目组。今天由我们四位来汇报这个项目的概要设计。

先简单介绍一下项目背景。不知道各位有没有玩过或听说过 GeoGuessr？这是一款 2013 年上线的网页游戏，它的玩法很特别——系统把你随机"丢"到世界某个角落的 Google 街景里，你要通过观察周围的线索——比如路牌上的文字是哪种语言、建筑是什么风格、植被是热带还是温带、道路是靠左还是靠右行驶——来判断自己大概在地球上的什么位置，然后在地图上标出来。系统根据你猜的位置和真实位置之间的距离打分。

这个游戏在全球有几千万玩家，但它有一个明显的问题：**题目是固定的，由官方团队创建，玩家只能被动消费内容。** 你想玩更多题目？等官方更新。你想做关于自己家乡的题目？做不了。你想和朋友对战？原生不支持。

我们的项目 GeoguessrEX 就是来解决这些问题的。它的定位是一个**以图寻游戏为载体的 UGC 社交平台**。

这里我想特别解释一下 UGC 这个概念。UGC 全称是 User-Generated Content，即"用户生成内容"。这其实是互联网产品里一个非常重要的模式——你们熟悉的 B 站、抖音、知乎，它们的内容不是平台自己做的，而是用户上传的。平台提供工具和规则，用户来创造内容，内容吸引更多用户，形成正向循环。

GeoguessrEX 把这个模式用在了地理猜谜上。用户不只是玩家，还可以成为出题者——用 Google 街景链接或自己拍的照片来创建题目。你的题目通过了审核，别人就能玩到；你的题库热门，还能在市场里卖出金币。这就是 UGC 的魅力——内容生态是活的，是用户共同建设的。

在这基础之上，我们又叠加了社交、竞技和经济系统——你可以加好友、发动态、打 PvP 对战、参与大逃杀、买卖题库、发布悬赏。最终形成的不是一个简单的答题工具，而是一个有内容、有关系、有成长的社区。

整体汇报大约 20 分钟，我们四个人按模块分工讲解。我先讲项目背景、整体架构和用户认证模块。

### Slide 2 — 项目背景与整体架构（2 分钟）

接下来看整体架构。我先讲技术架构，再讲业务架构。

**技术架构**上，GeoguessrEX 采用经典的三层分层设计。

最上层是前端层，基于 Vite + React 18。为什么选 React？因为我们需要大量的交互式地图操作——缩放、拖拽、标记、图层切换——React 的组件化模型非常适合管理这些交互状态。地图方面，我们同时接入了两个地图服务：高德地图用于国内用户的猜点标记和结果展示，Google 街景 API 用于加载 360 度全景画面。这里有一个重要的技术细节——中国的电子地图必须使用国家测绘局规定的 GCJ-02 加密坐标系，而 Google 街景的数据是国际标准的 WGS-84 坐标系，所以前端需要做坐标转换，这点后续引擎模块会详细讲。

中间层是后端，基于 Express 4 框架。Express 是 Node.js 生态最成熟的 Web 框架，选它不是因为多先进，而是因为它够用、够稳、团队都熟。后端承载了用户鉴权中间件、游戏评分引擎、PvP 房间状态管理、经济交易处理等核心业务逻辑，以 RESTful JSON API 的方式暴露给前端，跑在 3001 端口。

最底层是数据层，我们选了 SQLite 而不是 MySQL 或 PostgreSQL。这个选择可能看起来有点"不正规"，但我们是刻意为之。SQLite 不需要安装数据库服务、不需要配置连接、不需要运维——数据库就是一个文件。对于当前项目规模，这个优势太大了：开发环境直接拷走就能跑，部署不需要额外搭数据库服务器，备份只需要复制文件。驱动用 better-sqlite3，它提供同步 API，代码执行顺序与书写顺序一致，调试友好。

工程管理上，使用 pnpm workspace 做 monorepo——前端在 `apps/web`，后端在 `apps/api`，公共配置在根目录统一管理。

**业务架构**上，整个产品的核心玩法闭环是：系统从题库抽取题目 → 展示街景全景或用户上传的图片 → 用户观察场景线索（路牌文字、建筑风格、植被、车辆、道路标线等）→ 在地图上标记猜测位置 → 提交后系统用 Haversine 公式计算猜测点与真实点的球面距离 → 套用指数衰减模型算出分数 → 结果以双标记地图展示（正确答案 + 用户猜测）→ 结算排名。

这一闭环派生出了我们后面要讲的所有玩法模式——单人练习就是基础闭环不加限制；PvP 是两个人在这个闭环上同步竞技；大逃杀是多人在这个闭环上逐轮淘汰。模式不同，但底层引擎是一样的。

### Slide 3 — 功能模块全景（1 分钟）

从功能角度看，整个系统目前有 16 个核心模块，可以归入四大能力域。

第一个是**基础设施域**：用户认证、题库系统、游戏引擎——这是所有玩法和功能的底座。

第二个是**核心玩法域**：单人练习、PvP 对战、大逃杀、每日挑战、国家连胜——覆盖从休闲到硬核竞技的完整光谱，适应不同玩家群体。

第三个是**社交经济域**：好友系统、社区动态、评论点赞、虚拟钱包、题库市场、悬赏系统——这是平台从工具走向社区的关键层，也是 UGC 生态的商业化基础。

第四个是**平台运营域**：角色卡牌、赛季通行证、队伍系统、管理后台、寻宝游戏——提供长期留存抓手和内容运营工具。

**上篇**由我和下一位同学负责，聚焦基础设施和核心玩法——就是最根本的"怎么玩"的问题。

**下篇**由后面两位同学介绍社交经济、运营系统和底层技术架构——回答"怎么留住用户"和"怎么撑住系统"的问题。

### Slide 4 — 用户认证模块设计（2 分钟）

了解了全景之后，进入第一个核心模块：用户认证。

我们设计了**四级角色体系**，从低到高逐级递进授权。

第一级是**游客**。游客不需要注册账号，打开网站就能玩。但每天限制 3 局基础练习，数据不持久化——清除浏览器缓存后就没了。游客模式本质上是"试玩入口"，让新用户零门槛体验核心玩法，觉得好玩再注册。

第二级是**注册用户**，这是最核心的用户群。注册只需邮箱加密码，门槛很低。注册用户可以无限制体验所有游戏模式、上传自己的题目、参与社区互动、加入 PvP 对战和排行榜竞争。所有功能对他们全部开放。

第三级是**审核员**。随着用户上传题目增多，内容质量需要有专人把关。审核员由管理员任命，负责在后台查看待审题目、核实坐标准确性和内容合规性，做出通过或驳回的决策。他们是平台内容质量的守门人。

第四级是**管理员**，拥有全平台最高权限。管理员可以做用户管理、任命和撤销审核员、修改全局系统参数（比如市场费率、赛季周期、限时挑战的倒计时秒数），以及查看数据看板。

这四级角色形成一个渐进式的信任体系——游客零成本体验，注册用户用邮箱证明身份，审核员靠管理员信任授权，管理员由系统配置控制入口。

接下来是**安全设计**，这是认证系统的核心。

密码存储方面，我们绝对不存明文密码——这是基本原则。我们采用 PBKDF2 算法，密码加随机 16 字节 salt 后迭代 120,000 次 SHA-512 哈希。这个参数组合意味着什么？假设攻击者拿到了数据库文件，想通过暴力破解反推用户密码，即使是使用专业 GPU 集群，每秒也只能尝试几千次——每尝试一个密码就要跑 12 万次 SHA-512。对于正常用户登录，几百毫秒的延迟完全感知不到，但对于攻击者，这是无法逾越的计算量壁垒。PBKDF2 还有一个好处是防彩虹表攻击——每个用户的 salt 是随机生成的，即使两个用户密码完全相同，哈希结果也完全不同。

登录成功后，后端签发一个自定义的 Bearer Token 返回给前端。Token 结构是 `payload.signature`，payload 包含用户 ID 和角色信息，signature 是对 payload 的 HMAC-SHA256 签名。我们用自定义 Token 而不是标准的 JWT，是因为使用场景简单——只有一个后端服务，不需要跨服务传递或联合认证，自定义结构更轻量。密钥通过 AUTH_SECRET 环境变量注入，本地开发可以不设，但生产环境必须配置强密钥。Token 有效期 7 天，平衡安全性和便利性。

**权限控制**上，我们做到前后端双层拦截。

前端侧，AuthContext 是一个 React 上下文，在整个组件树中全局共享登录状态。用户登录后，AuthContext 存储 token 和用户信息，所有 API 调用通过 api.js 统一封装，自动附带 Authorization header。ProtectedRoute 组件在路由层做拦截——未登录用户访问需要权限的页面时，直接跳转到登录页，用户不会看到满屏的报错信息。

后端侧，authMiddleware 在每个请求到达业务处理函数之前执行：解析 Authorization header → 提取 token → 验证 HMAC 签名 → 解码 payload → 将用户信息注入 req.user。后续的服务层代码可以直接使用 req.user.id 和 req.user.role，不需要每个接口都重复写鉴权逻辑。adminMiddleware 是 authMiddleware 之后的第二层权限校验——它检查 req.user.role 是否是 admin，用于敏感操作如任命审核员、修改系统配置等。

这种双层设计的价值在于：前端的拦截提供体验保障，后端的拦截提供安全保障。即使前端出了漏洞、有人绕过了 ProtectedRoute，后端中间件依然会拒绝没有合法 token 的请求。两条防线互为补充，确保用户数据和系统安全。

到这里，项目的背景、整体架构和用户体系就介绍完了。下面请第二位同学介绍题库系统和游戏模块。

## 第2部分 · 汇报人 B（题库 + 游戏核心 + 三大玩法）

**对应 PPT**：概要设计上 Slide 5-10 ｜ **时长**：约 5 分钟

### Slide 5 — 题库系统模块设计（1.5 分钟）

题库系统是平台 UGC 生态的根基，采用题库→题目两级数据模型。

题目分两种类型：
- **街景模式**：存储 Google 街景的坐标、朝向、俯仰角、视野角、全景 ID，全部使用 WGS-84 坐标；
- **图片模式**：用户上传静态图片加手动坐标，适用于街景未覆盖的区域。

上传也有两种方式。第一种最便捷——粘贴 Google Maps URL，系统自动解析出坐标和视角参数填充表单；第二种是手动输入经纬度并上传图片。

所有题目提交后进入审核状态机：初始状态为 pending，审核员认领后查验坐标准确性、图片质量和内容合规性。通过则进入公共题库全员可用；驳回则通知上传者，填写修改意见，用户修改后重新提交。这个流程保证了题库的内容质量。

### Slide 6 — 游戏核心引擎模块设计（1 分钟）

游戏引擎是系统的计算核心，主要解决两个问题：怎么算分、怎么处理坐标。

评分采用指数衰减模型：`5000 × e^(-距离/2000)`。精确命中 0 公里得满分 5000 分；500 公里约 3894 分；2000 公里约 1840 分。距离越近分数越高，衰减速度先快后慢，符合直觉。

坐标处理涉及国内外合规问题。我们的管线是：题库存储原始 WGS-84 坐标 → 前端渲染时转为 GCJ-02 用于国内地图展示 → 用户标点后提交前转回 WGS-84 → 后端用 Haversine 公式计算球面距离。境外坐标直接透传不转换，保证全球精度一致。

### Slide 7 — 单人练习模块设计（30 秒）

单人练习是最基础的游戏形态，流程简单直观：

选择题库 → 展示街景/图片 → 地图标记 → 提交 → 后端计分 → 结算面板展示双标记地图 → 下一题。

每局可选择 3、5 或 10 题，无时间限制。结算面板展示总分、平均距离和最佳单题三个核心指标。

### Slide 8 — PvP 对战模块设计（1.5 分钟）

PvP 是核心竞技模块，我们设计了一套完整的 1v1 对战流程。

**流程**：A 创建房间生成 6 位房间码 → B 输入房间码加入 → 双方在 30 秒内选择角色和卡牌 → 进入多轮答题，同题同步出题 → 每轮公布得分 → 总分高者获胜。

房间有五个状态：waiting → ready → selecting → playing → finished，状态变更由后端统一驱动。

技能和卡牌的交互规则：被动技能全程自动生效，比如 Gambler 角色会使分数上下波动 20%；主动技能每局限用一次，需要手动触发；卡牌每轮最多用一张，传说卡使用后永久消耗。这套机制增加了策略深度——玩家需要权衡何时使用技能、出哪张卡牌。

### Slide 9 — 大逃杀模块设计（30 秒）

大逃杀模式是最具竞技张力的玩法：最多 8 人同时竞技，每轮所有人答同一道题，得分最低的玩家被直接淘汰。

一个有趣的机制是 Guardian 角色的被动——首次被淘汰时免疫一次，可以获得"复活"机会。

大逃杀完全复用 PvP 的角色和卡牌体系，用 br_rooms 和 br_players 两张表管理状态，降低系统复杂度的同时提供了截然不同的游戏体验。

## 第3部分 · 汇报人 C（轻量模式 + 角色卡牌 + 社交 + 经济 + 赛季）

**对应 PPT**：概要设计下 Slide 1-6 ｜ **时长**：约 5 分钟

### Slide 1（下）— 下篇封面（15 秒）

我接着介绍下半部分，涵盖每日挑战、角色卡牌、社交、经济、赛季通行证和管理后台等模块。

### Slide 2（下）— 每日挑战与国家连胜（1 分钟）

除了前面讲到的大型玩法，我们还设计了两款轻量模式来提升日活和留存。

**每日挑战**：全服统一推送 3 道题，所有玩家面对相同挑战，营造集体参与感。核心是签到打卡机制——连续参与解锁累积奖励，培养用户每日登录习惯。数据存储在 daily_challenges 和 check_ins 两张表中。

**国家连胜**：降门槛的趣味模式，只判定国家层级而不要求精确坐标。猜对继续累计连胜，猜错归零，按历史最高连胜进行全服排行。数据存在 country_streaks 表中。两种轻量模式成本低、频次高，是留存策略的关键。

### Slide 3（下）— 角色卡牌模块设计（1 分钟）

角色卡牌是平台的收集养成核心，6 名角色加 10 张卡牌构成完整体系。

角色分三个稀有度层级：Explorer、Hunter、Swift 三位普通角色提供基础增益；Seer 和 Guardian 两位稀有角色提供战术优势；Gambler 作为史诗角色，具有高风险高回报的双倍或归零机制。每个角色都有被动技能全程生效和主动技能每局限用一次。

卡牌方面：4 张普通提供基础增益，3 张稀有用于战术辅助，2 张史诗创造高风险高回报局面，还有 1 张传说卡"The Chosen One"——使用后直接获得满分 5000，但永久消耗。传说卡制造了稀缺感和使用决策的张力——是现在用掉还是留到关键对局？

### Slide 4（下）— 社交系统模块设计（1 分钟）

社交系统围绕三个层面构建：

**好友系统**：搜索用户 → 发送申请 → 对方同意 → 建立双向关注，数据基于 follows 表。

**社区广场**：玩家可以分享战绩卡片、发布失物招领、寻人启事或公告，支持图片上传，形成玩家自驱动的内容生态。

**互动体系**：评论支持嵌套回复形成讨论串；点赞采用 toggle 机制防止刷量；单向关注生成个性化时间线。

### Slide 5（下）— 经济系统模块设计（1 分钟）

虚拟经济闭环由三部分组成：

**钱包系统**：每位用户独立虚拟币余额，所有收支记录于 coin_transactions 流水表。充值提现接口已预留但目前为模拟环境。

**题库市场**：这是激励创作者的核心机制——用户上架自定义题库，买家购买，平台作为交易中介抽取 20% 佣金，卖家实收 80%。这个机制持续激励优质题库产出。

**悬赏系统**：创建者预设奖金池，提交时预扣，参与者提交答案后由发布者判定胜者，奖金全额转移。平台不抽成，纯激励性质。

### Slide 6（下）— 赛季通行证与队伍模块（45 秒）

赛季系统是长期留存的抓手：月度 20 级战令，XP 来自对局、挑战和社交互动，奖励覆盖金币、卡牌、角色和限定头像框。

配套 15 级用户成长体系，等级越高解锁越多角色槽位和卡组容量。队伍系统提供社交裂变——创建队伍、邀请成员、参与队伍排行榜竞争。

这部分讲完，最后请第四位同学介绍后台管理、数据库、接口和前端架构。

## 第4部分 · 汇报人 D（管理后台 + 数据库 + API + 前端 + 总结）

**对应 PPT**：概要设计下 Slide 7-10 + 即兴总结 ｜ **时长**：约 5 分钟

### Slide 7（下）— 管理后台模块设计（1 分钟）

管理后台是平台治理的中枢。我们设计了一个统一审核中台，所有内容类型——题库、社区帖子、悬赏任务、寻宝游戏——汇聚到统一的 reviews 审核表。

审核流程标准化：内容提交后进入待审队列 → 审核员认领并核实 → 做出通过或驳回的决策 → 系统自动通知创建者。

管理员还拥有人事管理能力（任命审核员、分配权限）、系统参数配置（限时活动、赛季参数、交易费率）以及数据看板实时监控运营指标。

### Slide 8（下）— 数据库结构设计（1 分钟）

数据库选型上，我们选择了 SQLite + better-sqlite3。

为什么是 SQLite？零配置、嵌入式、单文件便携，非常适合这个规模的项目。不用 ORM，直接写原生 SQL，透明可控。Schema 演进通过 migrate*() 函数管理，支持增量迁移，目前 27 张以上表覆盖全业务场景。

ER 关系可以概括为以 users 表为核心枢纽，向外辐射到题库、钱包、对战房间、社交互动、队伍、悬赏、赛季、寻宝游戏、通知审核等十大业务域，形成完整的关系型数据网络。

### Slide 9（下）— API 接口设计（1 分钟）

后端一共 17 个路由模块，覆盖全业务功能。列举几个核心的：auth 负责注册登录、questions 管理题库题目、submit 处理答案提交和评分、game-modes 承载 PvP 和 BR 对战逻辑、social 处理评论点赞关注、wallet 和 marketplace 支撑经济系统、season 管理赛季战令、leaderboard 提供多维度排行。

架构上采用 Routes → Services → Database 三层：路由层做请求校验和权限控制，服务层封装业务逻辑，数据库层执行 SQL 操作。三层解耦，便于测试和独立演进。

### Slide 10（下）— 前端架构设计（1 分钟）

前端一共 24 个页面，路由覆盖从登录认证到游戏、社交、市场、管理的完整用户旅程。

组件分为四个层级：地图层（GuessMap、ResultMap、StreetView）→ 游戏层（ResultPanel、BountyCard）→ 社交层（CommentSection、PostCard）→ 通用层（NavBar、ProtectedRoute、AuthContext）。

状态管理上，AuthContext 全局管理登录态和用户信息；api.js 做统一的 fetch 封装，自动附带 Authorization header，集中处理错误和 token 过期。

### 总结（1 分钟）

最后做个整体回顾。

GeoguessrEX 从 MVP 起步，目前已实现 16 个功能模块、27 张以上数据表、17 个路由模块、24 个前端页面，覆盖了从用户认证到社交经济、从单人练习到多人竞技的完整产品链路。

技术选型上，全栈 JavaScript、SQLite 轻量数据库、monorepo 工程结构，保证了开发效率和可维护性。

后续规划方向上，我们会重点推进对象存储迁移、测试体系建立、TypeScript 渐进迁移以及移动端适配。
