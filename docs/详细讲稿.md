## 第一部分：开场与基础架构（约 8-10 分钟）

### Slide 1 — 封面

各位老师好。我们是 GeoguessrEX 项目开发组，今天由我来向大家汇报这个项目的概要设计。

在进入技术内容之前，我想先花一点时间讲清楚这个项目"是什么"和"为什么做"，因为我觉得背景理解对于后续所有设计决策的把握都很关键。

不知道在座各位有没有玩过或听说过一款叫 GeoGuessr 的游戏？GeoGuessr 是 2013 年由一位瑞典程序员开发的网页游戏。它的核心玩法非常独特：系统把玩家随机"投放"到 Google 街景中的某个位置，玩家可以 360 度旋转观察周围环境——看路牌、建筑、植被、车辆、行人、道路标线，甚至天空的颜色——然后凭借这些线索推断自己在地球上的大致位置，在一张世界地图上点击标记。系统根据玩家标的位置与真实位置之间的距离来打分。距离越近，分数越高。

这个游戏一经推出就风靡全球，目前有数千万注册用户，并且在疫情期间经历了爆炸式增长——大家都被困在家里，通过这个游戏"云旅行"。它在教育领域也被广泛使用，很多地理老师用它来让学生直观地感受世界各地的风土人情。

那么，既然已经有了 GeoGuessr，我们为什么还要做 GeoguessrEX？因为原版有三个明显的痛点。

第一个痛点是**内容封闭**。GeoGuessr 的所有题目由官方团队创建，数量有限。玩家只能消费官方提供的内容，无法参与创作。你想做一套关于你家乡的题目？不行。你想做一套关于某个特定主题（比如"世界上最美的火车站"）的题库？不行。内容是单向流动的——从官方到玩家。

第二个痛点是**社交缺失**。GeoGuessr 本质上是一个单机游戏。虽然它后来加入了排行榜和简单的多人模式，但没有好友系统，没有社区动态，没有互动机制。你得了高分只能自己高兴，没法分享给朋友，没法形成讨论和互动。

第三个痛点是**玩法单一**。只有"看街景猜位置"这一个模式，没有对战竞技、没有养成收集、没有经济激励。用户来得快走得也快，缺乏长期留存的理由。

我们做 GeoguessrEX，就是针对这三个痛点，把 GeoGuessr 从一个"单机猜图工具"升级为一个"社区驱动的社交游戏平台"。而实现这个升级的核心钥匙，就是三个字母——**UGC**。

我想稍微展开讲一下 UGC 这个概念，因为它是整个项目设计的原点。UGC 是 User-Generated Content 的缩写，中文叫"用户生成内容"。这个概念其实大家非常熟悉——你们每天刷的抖音、B 站、小红书、知乎，它们平台上 99% 的内容都不是平台自己制作的，而是用户上传的。平台提供工具和规则，用户来创造内容，内容吸引更多用户，更多用户中又会涌现出更多创作者……这就是 UGC 的核心飞轮。

把 UGC 模式应用到地理猜谜上，会产生什么变化？用户不再只是"玩家"，他们同时也可以是"出题者"。你发现了一个有趣的街景角落，复制 Google Maps 链接，粘贴到我们的创建页面，系统自动解析出坐标和视角，你补充一个标题和几个标签，提交审核——通过之后，全球的用户都能玩到你出的这道题。如果你制作了一整套高质量题库（比如"日本京都寺庙合集"或者"欧洲小众火车站"），你可以把它上架到题库市场，设定一个金币价格。其他玩家觉得好就会购买，你赚取金币，平台抽取 20% 的交易费。这就形成了一个创作者经济的闭环。

有了 UGC 的内容基础之后，我们再往上叠加社交层（好友、社区、评论、点赞、关注）、竞技层（PvP 对战、大逃杀、国家连胜、排行榜）、经济层（钱包、市场、悬赏）和运营层（角色卡牌、赛季通行证、队伍系统）。最终形成的不是一个简单的猜图工具，而是一个有内容生态、有社交关系、有竞技成就、有经济循环的完整社区。

这就是 GeoguessrEX 的产品定位：**以图寻游戏为载体的 UGC 社交平台**。核心是"图寻游戏"，灵魂是"UGC"，价值锚点是"社交"。

今天整场汇报大约 25 到 30 分钟，我会按照功能模块逐一展开讲解。先从项目的整体架构开始。

### Slide 2 — 项目背景与整体架构

先看整体架构。我从技术架构和业务架构两个维度来讲。

**技术架构**上，GeoguessrEX 采用经典的三层分层设计。

最上层是**前端层**，基于 Vite 构建工具和 React 18 框架。之所以选 React，是因为我们的前端交互非常重——地图缩放拖拽、标记放置、街景旋转、多轮对战的实时状态切换——React 的组件化模型和虚拟 DOM 非常适合管理这些复杂的交互状态。地图方面，我们同时接入了两个地图服务：高德地图 JSAPI 用于国内用户的地图交互（猜点标记和结果展示），Google Maps Embed API 用于加载 360 度街景全景。这里有一个关键的技术细节需要提前说明——中国的电子地图按照国家测绘法规必须使用 GCJ-02 加密坐标系，而 Google 街景数据使用的是国际标准的 WGS-84 坐标，两者不兼容。所以前端必须负责坐标系转换，这一点在后面的游戏引擎模块会详细展开。

中间层是**后端层**，基于 Express 4 框架，提供 RESTful JSON API，跑在 3001 端口。Express 可能不是最"时髦"的框架，但它是 Node.js 生态中经过最长时间考验的 Web 框架——稳定、成熟、社区资源丰富、团队上手零成本。这一层承载了系统的核心业务：用户鉴权中间件、游戏评分引擎、PvP 房间状态管理、经济交易处理、赛季通行证逻辑等。对外暴露统一的 `/api/*` 前缀 RESTful 接口。

最底层是**数据层**。我们选择了 SQLite 数据库，这个选择值得多解释几句。为什么不用 MySQL 或 PostgreSQL？因为对于当前的开发阶段和项目规模，传统关系型数据库带来的运维成本完全是不必要的。SQLite 是嵌入式数据库——不需要安装数据库服务进程，不需要配置端口和连接字符串，不需要担心版本兼容和权限配置。数据库就是一个 .sqlite 文件，放在项目目录里。这对开发者来说太方便了——开发环境直接拷走就能跑，部署不需要额外搭建数据库服务器，备份和迁移只需要复制一个文件。驱动方面我们使用 better-sqlite3，它是 Node.js 生态中性能最好的 SQLite 驱动，提供同步 API——代码的执行顺序和书写顺序一致，不需要处理异步回调，对于业务逻辑的编写和调试都非常友好。

工程管理上，我们使用 pnpm workspace 管理 monorepo 结构。前端代码在 `apps/web` 目录，后端代码在 `apps/api` 目录，根目录统一管理依赖和公共脚本。两条线独立开发、独立打包、独立部署，通过 workspace 共享一些公共配置。这种结构比单一仓库更清晰，比多个独立仓库更便捷。

**业务架构**上，整个产品的核心玩法闭环非常简单但完整：系统从题库中随机抽取题目 → 前端加载 Google 街景 iframe 或展示用户上传的图片 → 玩家通过观察场景中的各种线索——路牌上的文字是什么语言、建筑是欧式还是亚洲风格、植被是针叶林还是热带棕榈、道路是靠左还是靠右行驶、车牌是长条还是方形、甚至天空的颜色和太阳的角度——综合推断地理位置 → 在高德地图上缩放、拖动、找到目标区域，点击放置标记 → 点击"提交"，前端将坐标发给后端 → 后端用 Haversine 公式计算猜测坐标与真实坐标之间的球面距离 → 套用指数衰减模型算出单题得分 → 返回给前端展示结果：一张双标记地图，绿色标注正确答案，红色标注用户猜测，同时展示距离公里数和本轮得分 → 进入下一题，直到全部题目完成 → 最终结算面板展示总分、平均距离、最佳单题。

这个闭环是所有游戏模式的基础。单人练习就是直接跑这个闭环。PvP 对战是两个人在同一组题目上各自跑这个闭环然后比较总分。大逃杀是多个玩家在同题上跑这个闭环然后每轮淘汰最低分。模式千变万化，但底层引擎统一。

### Slide 3 — 功能模块全景

了解了整体架构之后，再来看功能模块的全景图。

GeoguessrEX 目前涵盖了 16 个核心功能模块，我按照职责把它们归入四大能力域。

第一个是**基础设施域**：用户认证系统、题库系统、游戏核心引擎。这三个模块是平台的地基——没有它们，上面的所有玩法都跑不起来。用户认证解决了"谁在玩"的问题，题库解决了"玩什么"的问题，游戏引擎解决了"怎么算"的问题。

第二个是**核心玩法域**：单人练习、PvP 1v1 对战、大逃杀、每日挑战、国家连胜。五种模式覆盖了从最休闲到最硬核的完整用户光谱。单人练习适合新手入门和日常训练，PvP 和大逃杀满足竞技需求，每日挑战和国家连胜提供低门槛的碎片化玩法。

第三个是**社交经济域**：好友系统、社区动态、评论点赞、虚拟钱包、题库市场、悬赏系统。这一层是平台从"游戏工具"升级为"社交社区"的关键。有了社交关系，用户留下来不只是因为游戏好玩，还因为这里有朋友、有互动、有归属感。有了经济系统，创作者获得激励，UGC 飞轮才能持续转动。

第四个是**平台运营域**：角色卡牌系统、赛季通行证、队伍系统、管理后台、寻宝游戏。这些模块提供长期留存抓手和内容运营工具。角色卡牌给玩家收集和养成的目标，赛季通行证按月制造新鲜感，队伍系统促进社交裂变，管理后台支撑内容治理。

汇报结构上，上篇集中讲基础设施域和核心玩法域——也就是"怎么玩"的基础问题。下篇由后面的同学介绍社交经济域和平台运营域，以及底层的数据库、API 和前端架构——回答"怎么留住用户"和"怎么撑住系统"的问题。

### Slide 4 — 用户认证模块设计

现在进入第一个核心模块：用户认证。

认证系统的设计起点是一个问题：不同身份的用户，应该有不同的权限和使用边界。基于这个思考，我们设计了**四级角色体系**，从低到高逐级递进授权。

第一级是**游客**。游客不需要注册账号，打开网站就能开始体验基础的单人练习玩法。但我们设置了明确的限制——每天最多玩 3 局，数据不持久化存储，关闭浏览器后就没了。这个设计的意图很清楚：游客模式是"试玩入口"。我们希望潜在用户能以零成本体验到核心玩法的乐趣，建立"这游戏挺有意思"的第一印象后，再自然地引导注册。如果门槛太高——比如一打开就要注册——很多用户会直接关掉走人。但如果完全不限制游客——那谁还注册呢？3 局一天的额度是一个精心拿捏的平衡点。

第二级是**注册用户**，这也是平台最核心的用户群。注册非常简单——邮箱加密码加昵称，三个字段。注册之后，所有功能全部解锁：无限制体验所有游戏模式、上传自己的题目、参与社区互动、加入 PvP 对战和排行榜竞争。注册用户是平台内容贡献和社交互动的绝对主力。

第三级是**审核员**。随着平台成长，越来越多的用户开始上传题目，内容质量就需要有专人来管理和把关。审核员由管理员任命，他们获得了一项额外权限——在管理后台查看待审题目队列，逐题核实坐标准确性和内容合规性，做出通过或驳回的审核决策。他们是平台内容质量的守门人，审核标准直接决定了题库的整体品质。

第四级是**管理员**，拥有全平台最高权限。管理员可以做用户管理和角色分配（任命和撤销审核员）、系统参数配置（修改赛季周期、市场交易费率、限时挑战的倒计时秒数等全局参数），以及通过数据看板监控核心运营指标。

这四级角色的设计逻辑是"渐进式信任"——游客零信任、零成本；注册用户用邮箱建立了最低信任锚点；审核员获得了管理员授予的额外信任；管理员是系统初始的最高信任节点。角色之间有清晰的权限边界，互不越界。

接下来是**安全设计**，这是认证系统最核心的技术部分。

密码存储有两个铁律：绝对不能存明文密码，每个人的密码哈希结果必须不同。我们同时满足这两点：采用 PBKDF2 算法，将用户密码加上一个随机生成的 16 字节 salt，然后迭代 120,000 次 SHA-512 哈希。这个参数组合意味着什么？我们打个比方——普通哈希算法（比如单次 SHA-256）在 GPU 上每秒可以计算数十亿次，攻击者可以在几小时内暴力破解简单密码。但 PBKDF2 的 12 万次迭代是故意"慢"的——它把单次哈希的计算量放大了 12 万倍。对于正常用户登录，几百毫秒的延迟完全感知不到。对于攻击者，即使有专业 GPU 集群，每秒也只能尝试几千个密码。一个 8 位的混合密码，破解时间从几小时变成了几百年。另外，每个用户使用独立的随机 salt，即使两个用户恰好设置了完全相同的密码，数据库中存储的哈希值也完全不同——这从根本上防止了彩虹表攻击。

登录成功后的**会话管理**使用自签发的 Bearer Token。Token 的组成结构是 `payload.signature`——payload 是一段 base64url 编码的 JSON，包含用户 ID 和角色；signature 是对 payload 的 HMAC-SHA256 签名。我们选择自定义 HMAC Token 而不是标准 JWT，原因很实际：我们的使用场景只有一个后端服务，不需要跨服务 token 交换、不需要联合认证、不需要 JWT 的完整生态（JWKS、issuer、audience 等）。自定义结构更轻量、更透明、更容易调试。签名密钥通过 AUTH_SECRET 环境变量注入，本地开发时不强制设置，但生产环境必须配置高强度密钥。Token 有效期设为 7 天，这是一个在安全性和便利性之间平衡的典型选择——太短用户频繁重新登录体验差，太长一旦泄露风险大。

**权限控制**上我们实现了前后端双层拦截，两条防线互为补充。

前端侧，AuthContext 是一个 React Context，在整个组件树的根部提供全局登录状态。用户登录成功后，AuthContext 存储 token 和用户基本信息，所有后续的 API 调用通过 api.js 统一封装，自动在请求头中附带 `Authorization: Bearer <token>`。ProtectedRoute 组件在路由层面做拦截——未登录用户访问需要权限的页面时（比如 /pvp、/profile），组件检测到没有 token，直接重定向到登录页并提示"请先登录"。这层拦截是体验层面的——用户不会看到后端返回的 401 原始错误提示或一堆技术报错。

后端侧，authMiddleware 注册为全局中间件，在每个请求到达业务处理函数之前执行。它的执行过程是：从 Authorization header 中提取 token → 验证 HMAC 签名是否合法 → 解码 payload 获取用户信息 → 将 `{ id, role, nickname }` 注入到 `req.user` 对象 → 调用 `next()` 放行。后续的服务层函数可以直接通过 `req.user.id` 知道是谁在操作，通过 `req.user.role` 判断权限等级。adminMiddleware 是 authMiddleware 之后的第二层权限校验中间件——它检查 `req.user.role === 'admin'`，用于保护敏感操作如任命审核员、修改系统配置等。如果非管理员尝试访问，直接返回 403 Forbidden。

双层拦截的价值在于纵深防御。前端的拦截是体验保障——防止用户看到错误页面。后端的拦截是安全保障——即使有人绕过了前端路由直接调用 API（比如用 curl 或 Postman 发请求），后端中间件依然会拦截没有合法 token 的请求。两条防线互不依赖，任何一层失效另一层仍能兜底。

到这里，项目的背景定位、整体架构和用户体系就讲清楚了。下面进入第二部分，介绍题库系统和游戏核心引擎。

## 第二部分：题库与游戏核心（约 6 分钟）

### Slide 5 — 题库系统模块设计

题库系统是平台 UGC 生态的根基。没有题目就没有游戏，而高质量的题目来源不能仅靠开发团队手动录入，必须让用户参与共建。

数据模型采用题库→题目两级结构。**题库**是题目的集合容器，包含名称、描述、分类标签、难度等级和创建者信息。一个用户可以创建多个题库，每个题库可以包含多道题目。**题目**是核心实体，有两种类型。

街景模式题目基于 Google Street View 数据，存储七个关键字段：经纬度坐标、视角朝向（heading，0 到 360 度）、俯仰角（pitch，-90 到 90 度）、视野角度（fov，默认 100）、以及 Google 的全景 ID（panoId）。这些参数共同定义了用户在街景中能看到什么画面。为什么存储这么细？因为不同的朝向和视角会展示完全不同的场景，这些参数直接影响题目的难度。

图片模式题目适用于街景未覆盖区域——比如偏远地区、室内场景、特色景观等。用户上传 JPG、PNG 或 WebP 格式的图片，限制 10MB，同时手动输入拍摄地点的经纬度。这弥补了 Google 街景覆盖率的不足，对于中国用户来说尤其重要——国内很多地方没有 Google 街景数据。

上传题目我们设计了两种方式。第一种最便捷——用户只需在创建页面粘贴一段 Google Maps URL，系统自动解析出坐标和视角参数填入表单。目前支持三种 URL 格式：街景分享链接（带有 @ 符号的标准链接）、地点详情链接（place 路径）、以及 Embed 嵌入链接。解析逻辑在后端完成，前端只需把 URL 发过去，后端返回解析好的参数，用户再补充标题、标签等元信息即可提交。第二种方式是传统的手动录入——输入经纬度、上传图片、填写标题和描述。

但不管哪种上传方式，题目都不会直接进入公共题库。我们设计了一套完整的**审核状态机**。题目提交后初始状态是 pending（待审核），进入审核队列。审核员在管理后台看到待审列表后认领题目进行查验。查验内容主要有四个方面：坐标是否与图片吻合、坐标精度是否在合理范围内、图片是否清晰可辨、内容是否合规无违规。通过审核的题目状态变为 approved，进入公共题库，所有用户都能在游戏中被抽到。驳回的题目状态变为 rejected，审核员必须在 reviewNote 字段中填写详细的驳回原因——比如"坐标偏差约 500 米，请核实"或"图片模糊，建议更换高清图"——系统会向题目上传者推送站内通知。用户看到驳回原因后，可以在"我的题库"页面修改题目信息，重新提交，状态重置回 pending。

这个审核流程是平台内容质量的核心保障。没有审核，题库很快就会充斥低质量甚至错误的题目，用户的游戏体验会急剧下降。审核的存在也约束了上传者的行为——知道会被检查，上传时会更认真。

### Slide 6 — 游戏核心引擎模块设计

游戏引擎是系统的计算核心，我把它拆成两个子问题来讲解：怎么算分、怎么处理坐标。

**评分算法**的数学基础是 Haversine 公式。这是一个计算球面上两点之间最短距离的公式，考虑地球是一个椭球体，精度对于我们的应用场景完全足够。计算出的距离单位是公里。

但我们不直接拿距离当分数——那样太线性了，缺乏区分度。我们采用指数衰减模型：`score = max(0, round(5000 × e^(-distanceKm / 2000)))`。这里 5000 是满分参数，2000 是衰减常数。这个公式有一个很好的特性：距离近的时候，分数对距离非常敏感——0 公里精确命中满分 5000，10 公里误差就扣到约 4975，100 公里约 4756；而距离远的时候，分数趋于平稳——1000 公里约 3033 分，2000 公里约 1840 分。这种先快后慢的衰减曲线符合直觉：在附近找不到时，差 100 公里和差 200 公里确实差不多；但精确命中和差 10 公里是完全不同的体验。

**坐标转换管线**是另一个核心设计。问题的根源在于中国的地图测绘规范——国内地图服务（高德、百度等）必须使用 GCJ-02 加密坐标系，这是一种在 WGS-84 基础上加入非线性偏移的坐标系统。如果我们直接用 WGS-84 坐标在高德地图上展示，标记点会偏移几百米，对于猜位置游戏来说这个误差太大了。

我们的解决方案是建立一条清晰的坐标转换管线。题库中存储的始终是 WGS-84 坐标，这是国际标准，也是 GPS 设备直接输出的格式。前端在渲染时，先判断坐标是否在中国境内——如果在境内，调用 coordTransform.js 中的函数将 WGS-84 转为 GCJ-02 后再交给高德地图；如果不在境内，直接透传不做转换。用户在地图上点击放置标记后，高德返回的是 GCJ-02 坐标，我们在提交 API 请求之前，同样判断是否在中国境内，如果是则转回 WGS-84。后端收到的始终是 WGS-84 坐标，用 Haversine 公式计算距离，完全不关心坐标系转换的问题。

这个设计把坐标转换的复杂性完全封装在前端，后端只和 WGS-84 打交道，职责边界非常清晰。

### Slide 7 — 单人练习模块设计

单人练习模式是最基础的游戏形态。它承载了两个重要使命：一是作为新用户的入门体验，让他们在无压力环境下熟悉游戏机制；二是作为老用户的日常训练场。

流程设计得非常直白。用户首先从题库列表中选择一个感兴趣的题库——可以是官方精选题库，也可以是社区热门题库，还可以是自己创建的题库。选定后进入游戏主界面。

每一题的流程是：系统从题库中随机抽取一道尚未答过的题目，前端加载 Google 街景 iframe 或展示上传的图片。用户观察场景中的线索——可能是路牌上的文字、建筑物的风格、植被类型、道路标线颜色、车牌照格式等等——综合判断地理位置。用户在地图上点击放大缩小、拖动寻找目标区域，然后点击放置标记。点击"提交"按钮后，前端将猜测坐标发送给后端。

后端收到请求后执行计分逻辑。首先用 Haversine 公式计算猜测坐标与题目真实坐标的球面距离（公里），然后套用指数衰减公式算出单题得分，将本轮结果存入数据库，返回给前端。前端收到结果后，在结算面板上展示一张双标记地图——绿色标记是正确答案的位置，红色标记是用户的猜测位置——用户可以直观地看到自己偏差了多远。同时展示距离数值和本轮得分。

全部题目答完后进入终局结算，展示三个核心指标：累计总分、所有题目的平均距离、以及得分最高的那道题的详情。用户可以选择"再来一局"重玩当前题库，也可以选择"分享战绩"发布到社区。

可配置项包括每局题数（3、5 或 10 题可选）和题目来源（任意已审核通过的题库）。没有时间限制，用户可以慢慢观察、仔细推敲。对于新用户来说，这个无压力的环境是最好的学习场景。

### Slide 8 — PvP 对战模块设计

接下来是 PvP 对战模块，这是整个平台最核心的竞技系统。我花多一点时间来讲，因为它的设计复杂度最高。

**对战流程**分为五步。第一步，玩家 A 点击"创建房间"，后端生成一个 6 位数字房间码（比如 482915），写入 pvp_rooms 表，状态设为 waiting，A 进入等待页面。第二步，玩家 B 在首页输入这个房间码，后端校验房间是否存在且状态为 waiting，校验通过后将 B 加入房间，状态变为 ready，双方进入准备阶段。第三步，准备阶段有一个 30 秒的倒计时，双方各自从自己的角色列表中选择本局使用的角色，从卡牌收藏中选择本轮可用的卡牌。倒计时结束或双方都确认后，状态变为 selecting。这里设 30 秒是为了防止一方故意拖延——超时未选择则由系统随机分配。第四步进入正式对战，系统从题库中抽取题目，双方同时看到相同的街景或图片，各自在地图上标记猜测位置提交。每道题各自独立计分，一轮结束后公布双方本轮得分和累计总分。通常是 3 到 5 轮。第五步，全部轮次结束后比较总分——高者获胜。结果写入对战历史，双方都可以在个人主页回顾这场对决。

**房间状态机**有五个状态。waiting 表示房间已创建但对手未加入；ready 表示对手已加入等待开始；selecting 表示双方正在选择角色和卡牌；playing 表示正在答题中；finished 表示对战已结束。状态机设计的关键在于状态变更的后端统一驱动——前端只发送操作指令（如"我选好角色了"、"我提交答案了"），后端判断条件满足后推进状态，并通过响应通知前端。当前版本的状态同步是通过轮询 + 响应返回实现的，在后续规划中计划升级为 WebSocket 推送以降低延迟。

**技能与卡牌交互规则**是 PvP 的策略核心。每个角色有两个技能。被动技能全程自动生效，不需要玩家操作。比如你选了 Gambler 角色，每轮得分会自动在 ±20% 范围内随机波动——运气好能翻高，运气差会压低。主动技能每局限用 1 次，需要玩家在适当时机手动触发。比如 Hunter 的"精准定位"可以在某一轮让猜测点自动向正确答案偏移一定距离，提高该轮分数。何时使用主动技能是很重要的策略决策——是开局就用争取领先，还是留到最后一轮绝地翻盘？

卡牌系统增加了更多的策略维度。对战前玩家从自己的卡牌收藏中选择若干张带入对局。每轮答题时可以使用 1 张卡牌。卡牌的效果各异——有的增加本轮得分系数，有的缩小地图范围排除干扰区域，有的显示对手的大致位置。传说级卡牌"The Chosen One"最为特殊——使用后本轮直接获得满分 5000 分，但使用后这张卡牌从用户的收藏中永久消失。这意味着用户需要权衡：这场对局值不值得消耗这张极其稀有的传说卡？这种"一次性消耗品"的设计在卡牌游戏中很常见，能制造稀缺感和使用决策的紧张感。

---

### Slide 9 — 大逃杀模块设计

大逃杀模式是 GeoguessrEX 最具竞技张力的玩法。如果说 PvP 是 1v1 的技术对决，那么大逃杀就是多人混战的生存游戏。

基本规则是：2 到 8 名玩家进入同一个大逃杀房间。系统为这个房间抽取一道题目，所有人同时在相同题目上作答。一轮结束后公布排名，得分最低的玩家被淘汰出局。然后进入下一轮，剩余玩家继续比赛。如此反复，直到只剩最后一人存活，该玩家获得最终胜利。

这个"逐轮淘汰"的机制带来了递增的紧张感——随着玩家越来越少，每一轮的淘汰风险都在增大。特别是当只剩 3 个人的时候，每个人都知道自己这一轮答不好就直接出局，压力是真实存在的。

一个有趣的设计是 Guardian 角色的被动技能——首次被淘汰时免疫一次。这意味着选 Guardian 的玩家在被判定为最低分时可以"复活"一次，继续参与下一轮比赛。这个技能在大逃杀中非常强力，相当于比别人多一条命。但它的代价是 Guardian 在 PvP 中的主动技能没有那么强，所以这是一个策略取舍——你是愿意在大逃杀中多一条命，还是在 PvP 中有更强的进攻能力？

技术实现上，大逃杀用 br_rooms 表存储房间级别的信息（创建者、状态、当前轮次、题目序列），br_players 表存储每个玩家的状态（得分、是否存活、淘汰轮次）。角色和卡牌体系完全复用 PvP 的系统，不做重复开发。这种"复用现有系统、仅替换玩法规则"的设计思路降低了开发和维护成本——大逃杀本质上只是 PvP 的多人和淘汰制变体，核心的评分计算、角色技能、卡牌效果逻辑全部共用。

## 第三部分：轻量玩法与角色卡牌（约 5 分钟）

### Slide 下-1 / 下-2 — 每日挑战与国家连胜

除了前面讲的核心竞技模式，我们还设计了两款轻量玩法，目标是提升日活跃用户数和留存率。

**每日挑战**的核心设计理念是全服统一——每天由系统推送 3 道题目，全球所有玩家看到的都是相同题目。这意味着每个人面对的是公平的挑战，可以和朋友比较"今天的题你得了多少分"。配套的签到打卡机制是留存的核心——连续登录参与每日挑战的天数越多，获得的额外奖励越丰厚。第一天可能只给基础金币，连续 7 天额外奖励一张稀有卡牌，连续 30 天奖励限定头像框。这种"累积激励"机制在很多成功的产品中都得到了验证。

数据存储方面，daily_challenges 表记录每天的题目配置，daily_challenge_submissions 表记录每位用户每天的答题成绩，check_ins 表追踪签到连续天数。

**国家连胜**是与精确坐标玩法互补的"低门槛"模式。这个模式下，用户不需要精准标出位置——只需要判断这道题在哪个国家。比如看到题目的街景中有泰文招牌、靠左行驶、热带植被，就可以判断是泰国。猜对国家，连胜次数加一，进入下一题；猜错国家，连胜归零，从零开始。排行榜按历史最高连胜次数排名。

这个模式的设计目的是降低参与门槛。有些用户觉得精确标坐标太难——需要非常仔细地观察细节才能做到准确——但判断国家相对简单，更多依赖常识和宏观观察。国家连胜给这些用户提供了一个轻松但同样有成就感的游戏入口。

### Slide 下-3 — 角色卡牌模块设计

角色和卡牌是 GeoguessrEX 的收集与养成核心，它们为对战系统注入了策略深度和长期目标。

先说角色。目前设计了 6 名角色，分为三个稀有度层级。

普通层级有三位。Explorer 的被动让距离提示略微偏移，主动可以给额外积分；Hunter 的被动缩小范围提示的半径，主动能精准定位；Swift 的被动减少超时带来的惩罚，主动可以延长作答时间。

稀有层级有两位。Seer 的被动显示大致的区域轮廓帮助排除不可能的位置，主动可以去掉地图上的干扰标记；Guardian 的被动在大逃杀中免疫第一次淘汰，主动给一个护盾抵消一次卡牌负面效果。

史诗层级是 Gambler，被动让每轮的分数在 ±20% 范围内随机波动，主动是双倍或归零——要么这轮得分翻倍，要么这轮得零分。这是一个高风险高回报的角色，适合赌性强的玩家。

用户可以从自己拥有的角色中选择一个常驻，这个角色会影响在所有对战模式中的表现。

卡牌方面一共设计 10 张，普通 4 张、稀有 3 张、史诗 2 张、传说 1 张。卡牌的获取靠抽取，采用加权随机概率——普通卡抽出概率最高，传说最低。传说卡"The Chosen One"的效果是使用后本轮直接 5000 满分，但使用后永久从收藏中消失。这种"一次性神器"的设计在 TCG 游戏中非常经典——它给玩家带来巨大的短期优势，但使用它意味着放弃未来使用的可能性。玩家需要在此刻的对局和未来的可能性之间做决策。

## 第四部分：社交与经济系统（约 5 分钟）

### Slide 下-4 — 社交系统模块设计

社交系统是 GeoguessrEX 从工具走向社区的关键。

**好友系统**采用经典的"申请-同意"模式。用户通过昵称或 ID 搜索目标用户，发送好友申请；对方收到站内通知后选择同意或拒绝；同意后双方互为好友。好友列表展示头像、昵称、最近活跃时间和统计数据摘要（总局数、平均分）。数据存储在 follows 表中——我们用一条 follow 记录表示关注关系，双向关注即为好友。

**社区广场**是用户自驱动内容生态的载体。完成一局游戏后，用户可以点击"分享战绩"按钮，系统自动生成一张战绩卡片——包含最高分题目截图、总分、平均距离、排名百分位——用户可以附上一段文字感慨，然后发布到社区。除此之外，社区还支持发布失物招领、寻人启事和官方公告。图片上传通过 MediaUploader 组件实现，支持多图上传和预览。

**互动体系**包括三层。评论支持嵌套回复——用户可以回复某条评论，被回复的评论下方展示回复列表，形成讨论串。点赞采用 toggle 机制——点击一次点赞，再点一次取消点赞，防止重复刷量。关注是单向的——用户可以关注感兴趣的高手，在"关注"标签页看到他们最近分享的战绩和动态，形成个性化信息流。

社交系统的设计目标是让用户不只是在玩游戏，而是在一个社区中建立身份和关系——有好友、有粉丝、有互动，这些社交连接极大地提高了用户粘性。

---

### Slide 下-5 — 经济系统模块设计

经济系统由三部分组成：钱包、题库市场、悬赏系统。

**钱包**是经济系统的基础。每个注册用户自动拥有一个虚拟钱包，余额以"金币"为单位。所有金币变动通过 coin_transactions 流水表完整记录，包括交易类型、金额、关联业务 ID、时间戳，确保每笔账目可追溯。充值和提现接口已预留，但当前阶段为模拟环境——新用户注册赠送一定基础金币，后续可通过出售题库、赢取悬赏、赛季奖励等途径赚取。

**题库市场**是激励创作者的核心机制。用户可以将自己的原创题库上架到市场，设定一个金币售价。其他用户在市场中浏览、搜索感兴趣的题库，点击购买后系统自动从买家钱包扣款。这笔金币的分配是：卖家收到 80%，平台抽取 20% 作为"交易税"。这个 20% 的抽成比例参考了主流创作者平台的行业标准——足够让平台获得维持运营的收入，又不会太高导致创作者流失。市场的存在直接激励了用户创作高质量题库——好题库能卖出去，卖出去就有金币收入，金币可以买其他题库或者参与悬赏。

**悬赏系统**采用竞标模式。悬赏创建者在发布时设定悬赏描述（比如"帮我找到这张图片的确切拍摄地点"）和奖金池金额。系统在创建时从发布者钱包预扣奖金，确保资金到位。其他用户浏览悬赏列表，提交自己的答案。发布者查看所有提交后，选择自己认为正确或最佳的一份，标记为胜者。系统自动将预扣的奖金全额转给胜者——平台不抽成，这是纯激励性质，目的是促进用户之间的互动和知识分享。如果悬赏到期无人提交，预扣金币退还给发布者。

三部分共同构成了完整的虚拟经济闭环：用户通过创作和参与获得金币，通过消费和悬赏支出金币，平台通过抽成获得运营收入。

---

### Slide 下-6 — 赛季通行证与队伍模块

赛季系统和队伍系统是长期留存和社交裂变的抓手。

**赛季通行证**的设计思路参考了主流竞技游戏的 Battle Pass 机制。一个赛季持续一个月，包含 20 个等级。玩家通过完成对局、参加每日挑战、在社区互动等方式获得 XP。XP 累计到一定阈值后赛季等级提升，每次升级获得奖励——低等级给金币，中等级给卡牌，高等级给限定角色或头像框。到了月底赛季轮换，等级重置，战令内容更新，新的奖励阵容激励玩家继续参与。

**用户等级**是赛季系统之外的独立成长体系，共 15 级。XP 需求和升级难度逐级递增——第一级可能打 5 局就升了，但 14 级升 15 级可能需要数百局。等级影响的是功能性权益——解锁更多角色槽位，可以收集更多角色并在对战前自由切换；提升卡组容量，对战时能携带更多卡牌增加策略灵活性。

**队伍系统**支持创建队伍、邀请成员加入。队伍有独立的排行榜，按队伍成员的总分或平均分排名，激励组队玩家之间的协作和竞争。数据存储在 teams 表（队伍信息）和 team_members 表（成员关系）中。

## 第五部分：后台管理与技术架构（约 5 分钟）

### Slide 下-7 — 管理后台模块设计

管理后台是平台治理的中枢。我们设计了一个**统一审核中台**——不管用户提交的是什么类型的内容（题库题目、社区帖子、悬赏任务、寻宝游戏），都汇聚到统一的 reviews 审核表中处理。

reviews 表的设计是一张通用审核表，包含 target_type（审核对象类型，如 question/post/bounty/game）和 target_id（关联的业务数据 ID），以及 status、reviewer_id、review_note 等通用字段。这种设计避免了为每种内容类型单独建审核表和写审核逻辑——所有的审核流程共用一套代码，新增审核内容类型只需在 target_type 枚举中加一个值。

审核流程标准化为三阶段：内容提交后进入"待审"队列；审核员在后台看到待审列表，认领一条记录进行核实——核实的具体内容取决于类型（题目核坐标精度，帖子核内容合规）；根据核实结果做出"通过"或"驳回"的决策。驳回时必须填写审核备注说明原因。系统自动向内容创建者推送通知。

管理员还拥有三个额外能力：人事管理——任命和撤销审核员，分配审核权限；系统配置——调整限时挑战的倒计时秒数、赛季的起止日期和奖励参数、市场交易费率等全局参数；数据看板——实时监控核心运营指标如日活用户数、新增题目数、对局总数。

### Slide 下-8 — 数据库结构设计

数据库选型上我们选择了 SQLite + better-sqlite3，这是一个有意识的技术决策。

为什么不选 MySQL 或 PostgreSQL？因为对于当前阶段的项目规模，关系型数据库服务器的运维成本完全是不必要的。SQLite 是嵌入式数据库，不需要安装服务进程、不需要配置端口和连接、不需要担心版本兼容——数据库就是一个 .sqlite 文件，直接放在项目目录中，开发环境拷走就能跑。better-sqlite3 是 Node.js 生态中最成熟的 SQLite 驱动，它提供同步 API——不需要 await，代码执行顺序与书写顺序一致，对于业务逻辑的编写和调试都很友好。

我们刻意不使用 ORM。ORM 在大型项目中确实能提升开发效率，但对于我们这个项目——表结构的复杂度可控、查询大多简单直接——使用 ORM 反而增加了一层抽象开销，排查问题时需要在 ORM 生成的 SQL 和业务代码之间反复跳转。直接写 SQL 意味着数据库操作完全透明可控。

Schema 的版本演进通过 migrate*() 函数管理。最早的数据库只有几张表，每增加一个新功能模块，就新增一个 migrate 函数来创建对应的表和字段。比如 migrateV05 可能添加了赛季相关的三张表，migrateV06 给 users 表新增 xp 和 level 字段。所有迁移函数按版本顺序排列，启动时检查当前 schema 版本，按需执行未应用的迁移。这种增量迁移方式支持平滑升级——用户的数据不会丢失，新版本启动后自动更新到最新结构。

目前整个系统包含 27 张以上的表，核心是以 users 表为枢纽的关系网络。users 关联到题库（question_banks 和 questions）、钱包和交易流水（wallets、coin_transactions）、对战数据（pvp_rooms、br_rooms、br_players）、社交关系（comments、likes、follows）、队伍（teams、team_members）、悬赏（bounties、bounty_submissions）、赛季（season_pass）、每日挑战（daily_challenges、check_ins）、寻宝游戏（treasure_games、location_tasks、game_registrations、game_progress），以及通知（notifications）和审核（reviews）。

### Slide 下-9 — API 接口设计

后端一共 17 个路由模块，按照业务域划分，每个模块对应一个 URL 前缀。

核心的几个模块包括：auth 负责注册、登录和获取当前用户信息；questions 管理题库和题目的增删改查；submit 是游戏核心——接收用户提交的猜测坐标，调用评分引擎计算距离和分数并返回结果；game-modes 承载 PvP 房间管理、大逃杀房间管理和国家连胜逻辑；social 处理评论、点赞和关注；wallet 管理余额查询、充值和提现；marketplace 支持题库的上架、下架、购买；bounties 管理悬赏的创建、提交和结算；season 提供赛季战令数据；leaderboard 提供多维度的排行榜查询。

架构设计上严格遵循三层分离原则。最外层是**路由层**（Routes），负责 HTTP 请求的接收、参数校验和权限检查——比如检查请求体格式是否正确、必填字段是否缺失、当前用户是否有权限执行该操作。中间是**服务层**（Services），封装纯粹的业务逻辑——比如提交答案时的评分计算、购买题库时的余额扣减和转账、房间状态推进的条件判断。最底层是**数据库层**（Database），负责执行 SQL 操作和返回结果。

三层解耦带来的好处很明显。路由层可以单独测试权限逻辑（mock 服务层），服务层可以脱离 HTTP 上下文测试业务逻辑（直接传入参数），数据库层可以单独验证 SQL 正确性。每层的修改不影响其他层——比如把评分公式中的衰减常数从 2000 改成 2500，只需要改 gameService.js 中的一行，路由层和数据库层完全不受影响。

### Slide 下-10 — 前端架构设计

前端部分，目前一共 24 个页面路由，完整的路由树覆盖了从登录到游戏、社交、市场、管理的全链路。

主要页面包括：`/login` 登录注册页；`/` 首页，展示题库列表和模式选择；`/game/:groupId` 单人游戏页面；`/create` 题目创建；`/manage` 题库管理；`/pvp` PvP 对战入口；`/br` 大逃杀入口；`/daily` 每日挑战；`/bounties` 悬赏广场；`/games` 寻宝游戏中心；`/community` 社区动态；`/profile` 个人主页；`/leaderboard` 排行榜；`/marketplace` 题库市场；`/teams` 队伍管理；`/season` 赛季战令页；`/admin/reviews` 管理员审核台；`/notifications` 通知中心。

组件按职责分为四个层级。**地图层**是与地图和街景相关的组件——GuessMap 是可交互的猜点地图，ResultMap 是展示结果的双标记地图，GoogleStreetView 是街景 iframe 的封装。**游戏层**是游戏流程相关的组件——ResultPanel 展示单题和整局结算结果，BountyCard 展示悬赏卡片信息。**社交层**是社区互动相关的组件——CommentSection 管理评论列表和嵌套回复，PostCard 渲染社区动态卡片。**通用层**是跨页面共享的组件——NavBar 顶部导航栏，UserBar 用户信息和快捷入口，ProtectedRoute 路由守卫，AuthContext 全局登录态管理。

**状态管理**方面没有引入 Redux 或其他状态管理库。全局性的状态只有登录态和用户信息，通过 AuthContext 管理就够了。各页面的数据获取和展示用组件自身的 state 即可。API 调用统一通过 api.js 模块——它封装了 fetch，自动附带 Authorization header，统一处理 401 未登录、500 服务器错误等异常情况，并支持 token 过期后的自动刷新逻辑。

## 总结（约 2 分钟）

### 整体回顾

我们来做整体回顾。

GeoguessrEX 从一个基础的 MVP 起步，目前已经实现了 16 个功能模块、27 张以上的数据库表、17 个路由模块、24 个前端页面。功能覆盖从用户认证到社交经济、从单人练习到多人竞技的完整业务闭环。

在技术架构上，几个关键决策支撑了项目的快速迭代：全栈 JavaScript 统一了前后端语言栈，降低了团队协作成本；SQLite 的零配置特性免去了运维负担，让我们可以专注于业务功能的开发；monorepo 结构保证了前后端的独立性和协作效率；三层架构的分离让每个模块职责清晰、易于测试和维护。

在业务设计上，题库的 UGC 生态和审核机制解决了内容供给问题；多玩法覆盖了休闲到竞技的完整光谱；社交经济系统构建了用户粘性和社区氛围；角色卡牌和赛季系统提供了长期的收集目标和留存抓手。

后续规划上，我们有几个明确的方向：首先是对象存储迁移——当前图片存储在服务器本地，后续需要迁移到 OSS 或 S3 以支持大规模部署；其次是测试体系的建立——目前缺乏单元测试和集成测试，这是项目走向生产级必须补齐的；然后是 TypeScript 的渐进迁移——类型系统能显著减少运行时错误；以及 CI/CD 流水线的搭建和移动端的考虑——React Native 或微信小程序都是可行的方向。

以上就是 GeoguessrEX 概要设计的全部内容。谢谢各位老师，欢迎提问。
